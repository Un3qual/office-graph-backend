## ADDED Requirements

### Requirement: Database boundary threat model is explicit

Office Graph SHALL enforce direct low-level persistence and repository-authored
SQL boundaries across trusted project source and pinned dependencies. The
database-boundary gate SHALL NOT claim to sandbox arbitrary code executing in
the application VM.

#### Scenario: Generic execution has no direct database evidence

- **WHEN** tracked code uses an OTP callback, process, RPC, reflection,
  compilation, or shell API without directly referencing a database primitive
- **THEN** the database-boundary gate MUST NOT classify that generic executor as
  database access

#### Scenario: Untrusted execution becomes a requirement

- **WHEN** Office Graph must execute code that is not trusted to follow project
  architecture policy
- **THEN** that code MUST run outside the application OS process without the
  application's database credentials or database network access

## MODIFIED Requirements

### Requirement: Non-migration database access is fully approved

Office Graph SHALL have zero unapproved direct raw-SQL or direct-Ecto
occurrences in runtime code, tests, test support, Mix tasks, configuration,
seeds, or scripts. Explicitly approved exceptions SHALL remain exact,
fingerprinted, provenance-backed, and behavior-tested.

#### Scenario: Non-migration source is scanned

- **WHEN** canonical verification scans a tracked source outside
  `priv/repo/migrations`
- **THEN** every explicit low-level database primitive MUST be removed in favor
  of an owning Ash interface or match an exact approved exception

#### Scenario: Compiled project modules are audited

- **WHEN** a tracked project module compiles a direct import or call to Repo,
  Ecto SQL, Postgrex, DBConnection, or another classified persistence module
- **THEN** canonical verification MUST report it unless the source occurrence is
  approved or the caller is an explicit repository infrastructure owner

#### Scenario: Terminal repository scan completes

- **WHEN** canonical verification scans the current repository
- **THEN** every detected occurrence MUST match an exact explicitly approved
  exception or fail without consulting or rewriting a temporary debt inventory

#### Scenario: Approved inventory repeats one locator

- **WHEN** two approved entries share the same path, line, class, construct,
  function, and ordinal even when their fingerprints differ
- **THEN** canonical verification MUST reject the approved inventory before
  matching current fingerprints or suppressing stale entries

#### Scenario: Approval provenance is invalid

- **WHEN** an approved exception references missing, invalid, unmatched, or
  ambiguous OpenSpec approval evidence
- **THEN** canonical verification MUST reject the approved inventory before
  matching current fingerprints or suppressing stale entries

#### Scenario: Framework capability is insufficient

- **WHEN** implementation cannot safely express one exact occurrence through
  the pinned Ash and AshPostgres versions
- **THEN** work on that occurrence MUST stop until a later accepted OpenSpec
  change records its exact fingerprint and explicit user approval

### Requirement: Migration baseline has no removal debt

Office Graph SHALL have zero unapproved raw-SQL or direct-database occurrences
in its terminal migration baseline. Migrations SHALL be generated by
AshPostgres or remain within a finite declarative Ecto migration syntax.

#### Scenario: Generated migration state is checked

- **WHEN** canonical verification validates migrations
- **THEN** it MUST run `mix ash_postgres.generate_migrations --check` without
  mutating the worktree

#### Scenario: Migration source is scanned

- **WHEN** a migration contains a helper, arbitrary control flow, direct
  repository call, external SQL file, raw SQL, or dynamic SQL-bearing option
- **THEN** verification MUST reject it unless the exact low-level occurrence and
  its required static context are explicitly approved

#### Scenario: Terminal migration baseline is compared

- **WHEN** migrations and release setup complete on an empty PostgreSQL 18
  database
- **THEN** verification MUST compare every relevant project-owned terminal
  object with Ash/resource ownership metadata and reject extras, omissions, or
  definition drift

#### Scenario: Native UUIDv7 default remains necessary

- **WHEN** the PostgreSQL 18 `uuidv7()` default remains represented by either
  previously approved generated fragment
- **THEN** the approved inventory MUST retain its exact provenance and the
  scanner MUST invalidate approval when the fragment or approved loop context
  changes
