## Context

The existing project gate attempts to infer whether arbitrary Elixir and Erlang
execution can eventually reach persistence. It models callback arguments,
container flow, process state, OTP startup, reflection, compiler entrypoints,
and migration behavior. The implementation is larger than the architecture it
replaced and still cannot prove the absence of an indirect database call.

Office Graph is a modular monolith built from trusted first-party source and
pinned dependencies. It does not execute untrusted extensions in the
application VM. The enforceable project requirement is therefore that
repository-authored code has no direct low-level persistence dependency or raw
SQL unless the exact occurrence is approved.

## Goals / Non-Goals

**Goals:**

- Keep database enforcement strict and fail closed over the finite evidence
  each gate claims to inspect.
- Keep exact exception fingerprints, provenance, behavior verification, and
  retirement metadata.
- Preserve the two approved UUIDv7 fragments and invalidate their approval when
  either fragment payload or its approved migration context changes.
- Cover tracked runtime code, tests, support modules, Mix tasks, configuration,
  seeds, migrations, scripts, and SQL-like files.
- Detect compiler-resolved low-level dependencies introduced by aliases,
  imports, or macro expansion without teaching the source gate alias flow.
- Compare the migrated terminal database with resource ownership across every
  relevant project-owned PostgreSQL object class.

**Non-Goals:**

- Proving that arbitrary or malicious code in the BEAM cannot reach a database.
- Treating generic callbacks, processes, RPC, reflection, compilation, or shell
  APIs as database access without a direct database primitive.
- Symbolically executing helpers, SQL bodies, callbacks, control flow, or
  migration lifecycle.
- Adding raw SQL, schema behavior, dependencies, or product APIs.

## Decisions

### 1. The boundary governs trusted source, not arbitrary in-process code

Project code and locked dependencies are trusted to participate in static
governance. A deliberate attempt to conceal database access behind generic
runtime execution is outside this linter's security claim. If Office Graph
later runs untrusted extensions, persistence must move behind a separate OS
process or service that alone receives database credentials and network access;
an OTP application boundary in one VM is not credential isolation.

This choice makes the gate an architecture contract rather than an incomplete
language sandbox.

### 2. The source gate recognizes only explicit finite primitives

The source scanner parses every tracked Elixir source and recognizes direct or
fully qualified calls to `OfficeGraph.Repo`, Ecto SQL and migration APIs,
Postgrex, DBConnection, Ecto.Multi, query fragments, SQL-bearing Ecto and
AshPostgres DSL settings, and migration raw-SQL constructs. SQL-like tracked
files are exact whole-file raw-SQL occurrences. Aliases, imports, delegates,
captures, or reflection that target a low-level database module are rejected as
unsupported indirection rather than followed through source dataflow.

Tracked executable scripts use one language-neutral forbidden-token gate. A
PostgreSQL client token in an executable script is rejected without deciding
whether shell quoting, a heredoc, JavaScript chaining, Python lists, or another
language construct would execute it. The policy intentionally accepts this
conservative source restriction to avoid maintaining language parsers.

The scanner does not follow aliases, variables, helper return values,
callbacks, containers, process messages, or dynamic module construction. An
approved low-level call must therefore use the explicit source form the gate
can fingerprint. A direct call with a nonliteral SQL payload is still detected
but cannot be approved because its behavior is broader than its source
fingerprint.

Migration entrypoints use a finite declarative allowlist. Helpers, arbitrary
control flow, direct repository calls, external SQL files, and dynamic
SQL-bearing option values fail closed. The two historical UUIDv7 loops are
accepted only when their complete approved static context matches.

### 3. Compiled auditing uses BEAM import metadata

Canonical verification builds test and production modules with debug metadata,
then reads BEAM `:imports` and `:compile_info` chunks. Any direct dependency
from a tracked project module to a low-level database module must correspond to
an explicit source occurrence or belong to one of two structural owners:

- `OfficeGraph.Repo`, whose implementation is generated by AshPostgres; and
- `OfficeGraph.Application`, which starts the repository and installs Ecto's
  development logger.

The audit does not disassemble instructions, resolve line tables, inspect
abstract control flow, or infer callback targets. BEAM imports are module-level
compiler-resolved evidence. Source aliases and imports that could make that
evidence ambiguous are prohibited, so the audit does not need source/BEAM
dataflow reconciliation.

### 4. Migration generation and terminal state remain independent gates

`mix ash_postgres.generate_migrations --check` remains the source of truth for
resource/snapshot drift. The migration baseline is then executed against
PostgreSQL 18 and compared with expected Ash/resource ownership metadata.

Terminal comparison covers schemas, tables and partitions, columns, primary
and foreign keys, constraints, indexes, sequences, enums, views and
materialized views, routines, triggers, RLS state and policies, grants, and
extensions where project-owned. Database-owned `pg_dump` output is used so the
repository adds no catalog SQL exception.

### 5. Exceptions prove both source identity and behavior

The canonical approval inventory remains the only suppression mechanism. Every
entry requires path, function, line, ordinal, class, construct, fingerprint,
approving change, owner, reason, verification, and retirement condition. The
approving change contains an identical evidence record. Low-level exceptions
also name any intentional terminal object effects and have focused behavior
tests; terminal equality alone is not data-plane evidence.

## Risks / Trade-offs

- **A malicious trusted module can hide a call behind runtime dispatch.** This
  is an explicit threat-model limit; pinned dependency review and ordinary code
  review govern deliberate obfuscation. Untrusted code requires process and
  credential isolation.
- **A new AshPostgres DSL can carry SQL without being listed.** The source
  primitive table is reviewed when AshPostgres is upgraded, while generated
  migration drift and terminal comparison provide independent detection.
- **BEAM metadata can be missing or stale.** Canonical verification compiles
  both environments first and fails when a tracked project BEAM lacks readable
  import/source metadata.
- **Terminal dump parsing can drift with PostgreSQL.** PostgreSQL 18 is pinned
  in the flake, dump fixtures cover all supported object classes, and unknown
  project-owned statements fail closed.

## Migration Plan

1. Publish a foundation PR from `main` containing this change, the bounded
   source primitive gate, and the module-level BEAM dependency audit. Keep the
   old enforcement active in parallel.
2. Publish a migration-conformance PR stacked on the foundation. Add the
   AshPostgres drift and terminal PostgreSQL inventory layers without source
   or migration interpretation.
3. Publish a cleanup PR stacked on migration conformance. Switch canonical
   enforcement to the replacement layers and delete the symbolic scanner,
   migration interpreter, and synthetic semantic fixtures only after the
   replacement stack passes.
4. Close superseded PR 37 with links to all replacement PRs. Do not retarget or
   reuse its implementation branch.

Rollback is a branch/PR rollback; no product data or schema changes are made.
